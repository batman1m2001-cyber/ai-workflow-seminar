Chapter 8 · Agents hit a wall

Every decision the model makes is a model call: time, tokens, and one more chance to go wrong. In Part I, one research question took 4 calls; three questions took 11 for a single email. Now scale it the way the course brief does, and let the model decide every box.

Why the 7 agents lose facts

The research, calendar and company agents find the facts. Then the Memory Agent, an LLM, rewrites everything into one summary, and some facts don't survive. A merge written in code can't drop a fact.

The truth

The more steps the model decides, the slower, costlier and less reliable the system. Let the model decide only where the path can't be known, and let code decide the rest.

Chapter 9 · An agent is a graph with a loop

Draw the Part I agent as a graph and it's tiny: llm, run_tool, and an edge back. The only special thing is who picks that edge: the model. Everything around it, the gate, the triage, the notes, the merge, the brief, is a graph whose edges your code picks.

The truth

An agent is a workflow with one loop whose edge the model picks. A real system is a bigger workflow with that loop as one node. So the question is no longer how many agents: it's what runs the workflow.

Nodes and edges

Forget email for a moment. Every workflow is two things: nodes that do the work, and edges that say which output feeds which input.

The truth

A workflow is nodes with inputs and outputs, joined by edges. An LLM call, a tool, an agent and a person are all just kinds of node. The node does its job; the graph decides what runs next.

At run time, something has to do that deciding: keep every output, see which node is ready, run nodes side by side, wait for a person, retry what failed, record it all. That something is a workflow engine.

Chapter 10 · Inside a workflow engine

Seven layers. Triggers start runs. You define the graph, and the compiler checks and plans it once. The runtime core runs it: the scheduler decides what may run, the executor runs it. Nodes call integrations. Data lives in state and storage. Observability lets you see and steer it, and safety wraps all of it.

The life of one run

  1. Trigger. Linh's email hits the webhook; the run manager opens a run with an id, the email as input, and a context.
  2. Plan. The graph was compiled once at deploy: validated, loops rewritten, every node's ready count known.
  3. Schedule. The scheduler finds the nodes whose inputs are all in: the gate first.
  4. Execute. The executor runs them as async tasks, under the concurrency cap; an LLM node calls a provider, a tool node calls MCP.
  5. Write. Each result goes to the state store, at its node's address; the scheduler counts it against the next nodes, and fires those that are ready.
  6. Branch, loop, fan out. Flow control picks the branch, repeats the loop, runs the three researchers side by side and joins them.
  7. Fail well. A failed node is a value, not a crash; a retry or a fallback runs; the other branches go on.
  8. Pause. At human approval the run stops with a draft and a link (or an interrupt + checkpoint); the click resumes it.
  9. See it. Every node emitted a span: Studio draws the run, metrics count the tokens and cost, the eval set gates the next deploy.

LangGraph, inside: supersteps

All nodes share one dict, and several nodes may write the same key. To keep that safe, LangGraph runs the graph in supersteps (the Pregel model):

  1. find the nodes whose inputs changed in the last step;
  2. run them in parallel;
  3. wait until every one of them has finished;
  4. merge their writes into the dict (reducers, in a fixed order) and save a checkpoint;
  5. repeat.

What that buys: a consistent snapshot after every step, so it can resume, time-travel, or pause for a human with interrupt(). What it costs: every step waits for its slowest node.

The code it asks you to write

# one dict for the whole graph
class State(TypedDict):
    email: dict
    lead: dict
    notes: Annotated[list, operator.add]   # many writers: a reducer

# a node reads the dict, returns an update
def triage(state: State) -> dict:
    return {"lead": parse(llm(triage_prompt(state["email"])))}

g = StateGraph(State)
g.add_node("triage", triage)
g.add_node("recall", recall)
g.add_node("calendar", calendar)
g.add_node("brief", brief)
g.add_edge(START, "triage")
g.add_edge("triage", "recall")
g.add_edge("triage", "calendar")
g.add_edge(["recall", "calendar"], "brief")
app = g.compile(checkpointer=InMemorySaver())

OperonX, inside: dataflow

OperonX also keeps one shared state for the run, but every value has its own address: (op, output, context). Context is main, a loop iteration, or a stream item like [1]. Each op writes only its own slots and reads others' by reference (op["x"]); a slot that really is shared gets a reducer.

So there is nothing to wait on. Each op emits its results as events; the scheduler counts them against each successor, and a successor whose count reaches zero starts right away. A fast branch runs ahead, and a stream's item 1 is downstream while item 2 is still being made.

The code it asks you to write

# a node: a function that owns its outputs
@op
def triage(email: dict) -> dict:
    return {"lead": parse(llm(triage_prompt(email)))}

@graph
def prepare(email):
    lead = triage(email=email)
    notes = recall(lead=lead["lead"])     # reads triage's slot
    meetings = calendar(lead=lead["lead"])
    brief = write_brief(lead=lead["lead"], notes=notes["notes"],
                        meetings=meetings["meetings"])
    START >> lead >> [notes, meetings] >> brief >> END

Why OperonX

We built OperonX because the workflow is the product, and the engine under it should be fast, terse, and ours to bend the same week.

The honest line

LangGraph is stronger at durable checkpoints (resume after a crash, pause for days) and has the bigger ecosystem. We pay for OperonX too: we maintain it.
