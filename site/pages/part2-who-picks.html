Chapter 8 · Agents hit a wall

Every decision the model makes is a model call: time, tokens, and one more chance to go wrong. In Part I, one research question took 4 calls; three questions took 11 for a single email. Now scale it the way the course brief does, and let the model decide every box.

Why the 7 agents lose facts

The research, calendar and company agents find the facts. Then the Memory Agent, an LLM, rewrites everything into one summary, and some facts don't survive. A merge written in code can't drop a fact.

The truth

The more steps the model decides, the slower, costlier and less reliable the system. Let the model decide only where the path can't be known, and let code decide the rest.

Chapter 9 · An agent is a graph with a loop

Draw the Part I agent as a graph and it's tiny: llm, run_tool, and an edge back. The only special thing is who picks that edge: the model. Everything around it, the gate, the triage, the notes, the merge, the brief, is a graph whose edges your code picks.

The truth

An agent is a workflow with one loop whose edge the model picks. A real system is a bigger workflow with that loop as one node. So the question is no longer how many agents: it's what runs the workflow.

Chapter 10 · Inside a workflow engine

Every engine, LangGraph, OperonX, Temporal, Airflow, is these five parts. Three are plumbing. Two decide how the engine behaves: where the outputs live (state) and when a node may run (the scheduler).

Two engines, the same five parts, two different answers to state and the scheduler.

LangGraph, inside: supersteps

All nodes share one dict, and several nodes may write the same key. To keep that safe, LangGraph runs the graph in supersteps (the Pregel model):

  1. find the nodes whose inputs changed in the last step;
  2. run them in parallel;
  3. wait until every one of them has finished;
  4. merge their writes into the dict (reducers, in a fixed order) and save a checkpoint;
  5. repeat.

What that buys: a consistent snapshot after every step, so it can resume, time-travel, or pause for a human with interrupt(). What it costs: every step waits for its slowest node.

OperonX, inside: dataflow

OperonX also keeps one shared state for the run, but every value has its own address: (op, output, context). Context is main, a loop iteration, or a stream item like [1]. Each op writes only its own slots and reads others' by reference (op["x"]); a slot that really is shared gets a reducer.

So there is nothing to wait on. Each op emits its results as events; the scheduler counts them against each successor, and a successor whose count reaches zero starts right away. A fast branch runs ahead, and a stream's item 1 is downstream while item 2 is still being made.

Why OperonX

We built OperonX because the workflow is the product, and the engine under it should be fast, terse, and ours to bend the same week.

The honest line

LangGraph is stronger at durable checkpoints (resume after a crash, pause for days) and has the bigger ecosystem. We pay for OperonX too: we maintain it.
