def prepare(email):
    """The whole job, step by step."""
    if attack := screen(email):
        return f"held at the gate ({attack!r}): no model saw this email"
    lead = parse(llm(build_prompt(email)))
    notes = recall(f"{lead['company']}: {lead['intent']}")
    crm = start_mcp()
    tools = list_tools(crm) + LOCAL_TOOLS
    findings = merge(research_team(crm, tools, lead))
    return llm(brief_prompt(lead, notes, findings))

Chapter 11 · Monday breaks it

Harden it by hand: the iceberg

Every wound has a known fix, and none of them is about the model. Add them all and the 15-line agent is 150 lines. The loop is the tip; underneath is the execution system: timeouts, retries, failures as values, bounded parallelism, gates, traces, evals, approvals, durable state.

The truth

That list has a name: a workflow engine. The teams building agent frameworks reached the same answer: Microsoft's Agent Framework is built around graph workflows, the OpenAI Agents SDK runs on durable-execution engines underneath, and LangGraph has been a workflow engine all along.

Every line of this list answers a Monday wound. Hold any engine to it. If your agent runs in production, something does all of this: the only choice is whether it's an engine, or 150 lines per agent.

OperonX: the workflow, given to an engine

Part I ended on a picture: agent.py's functions joined by arrows. OperonX is a Python workflow engine that takes that picture literally:

@opa plain function becomes a step: recall, screen, request_approval
@graph and >>the wiring is written once: a >> [b, c, d] >> e runs b, c and d side by side, then e
if_(…)a branch the code picks; an agent node is where the model picks
the engineeach step runs the moment its inputs are ready; failures are values; timeouts, retries, bounded parallelism
around itwebhooks and schedules start runs, a golden set gates deploys, every run is a trace, and Studio draws the graph from the code

Every Monday wound from tab 1 has a line in that list. That's the difference between agent.py and a system: not the model, the engine around it.

The landscape, fairly

LangGraph is a good engine and the best supported. Temporal-class engines win when a run must survive for days. We built OperonX for speed and terse graphs, and we pay for it: we maintain it, and it serves one team. The measured numbers and the same system built in both are in the appendix.
