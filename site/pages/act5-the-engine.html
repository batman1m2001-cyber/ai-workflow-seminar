What an engine must do

The list is the real thesis of this talk, more than any product: steps and edges, branches, loops, bounded parallelism, failures as values, durable state, traces, evals as gates, human approval, jobs and services. If your agent runs in production, something does all of this. The only choice is whether it's an engine or 150 lines per agent.

The landscape, fairly

LangGraph is a good engine and the best-supported one. Temporal-class engines win when a run must survive for days. We use OperonX for the reasons on the next tab, and we pay for it: we maintain it, and it serves one team.

Why we built OperonX

Speed. Each step runs the moment its inputs are ready: no waiting for a whole round of steps, no merging the full state between rounds. An LLM call (hundreds of ms) dwarfs that overhead in one conversation; it matters for batch (10,000 calls a night), streaming (voice, per-chunk steps) and many small steps. We measured it on the meeting-prep golden set too: both engines take about 14.5 s, because the model dominates.

OperonX: the graph is the code

@graph
def prepare(email, deliver):
    gate = ops.screen(email=email)
    stop = ops.blocked(reason=gate["reason"])
    read = ops.letter(email=email)
    triage = LLMOp.of(
        resource="assistant",
        prompt={"system": TRIAGE, "user": "{letter}"},
        fields=["is_lead: bool", "intent: str", "contact: str"],
        parser="json",
        on_failure="error",
        letter=read["text"],
    )
    skip = ops.not_a_lead(intent=triage["intent"])

    who = ops.identify(email=email)
    crm = ops.crm(company_id=who["company_id"])
    cal = ops.calendar(company_id=who["company_id"])
    memory = ops.recall(company=who["company"])
    asks = ops.research_tasks(company=who["company"])
    website = researcher()(messages=asks["website"])
    news = researcher()(messages=asks["news"])
    people = researcher()(messages=asks["people"])

    facts = ops.evidence(
        email=email, company=who["company"], contacts=crm["contacts"], history=crm["history"],
        meetings=cal["meetings"], memory=memory["memory"],
        website=website["final"], news=news["final"], people=people["final"],
    )
    brief = LLMOp.of(
        resource="assistant",
        prompt={"system": BRIEF, "user": "Company: {company}\n\nEvidence:\n{evidence}"},
        company=who["name"],
        evidence=facts["text"],
    )
    check = ops.check_brief(brief=brief["content"], company=who["company"])
    ask = ops.request_approval(email=email, company=who["company"], brief=brief["content"], deliver=deliver)
    hold = ops.held(company=who["company"], brief=brief["content"], problems=check["problems"])
    done = ops.settle(a=stop["outcome"], b=skip["outcome"], c=ask["outcome"], d=hold["outcome"])

    START >> gate >> if_(gate["blocked"] == True, stop).else_(read)  # noqa: E712
    read >> triage >> if_(triage["is_lead"] == False, skip).else_(who)  # noqa: E712

    asks >> [website, news, people]

    facts >> brief >> check >> if_(check["ok"] == True, ask).else_(hold)  # noqa: E712

LangGraph: a state class, then nodes wired by name

class State(TypedDict, total=False):
    email: dict
    deliver: bool
    thread: str
    reason: Optional[str]
    is_lead: bool
    intent: Optional[str]
    company: Optional[dict]
    contacts: list
    history: list
    meetings: list
    memory: list
    research: Annotated[dict, operator.or_]  # three agents write here in parallel
    evidence: str
    brief: str
    problems: list
    outcome: dict
    decision: str


def build(checkpointer: Any = None):
    g = StateGraph(State)
    for name, fn in [("screen", screen), ("blocked", blocked), ("triage", triage), ("not_a_lead", not_a_lead),
                     ("identify", identify), ("crm", crm), ("calendar", calendar), ("recall", recall),
                     ("website", research("website", "what it does and sells")), ("news", research("news", "news")),
                     ("people", research("people", "team")), ("evidence", evidence), ("brief", brief),
                     ("check", check), ("held", held), ("request_approval", request_approval),
                     ("wait_for_sales", wait_for_sales), ("finish", finish)]:
        g.add_node(name, fn)
    fan = ["crm", "calendar", "recall", "website", "news", "people"]
    g.add_edge(START, "screen")
    g.add_conditional_edges("screen", lambda s: "blocked" if s.get("reason") else "triage", ["blocked", "triage"])
    g.add_conditional_edges("triage", lambda s: "identify" if s["is_lead"] else "not_a_lead", ["identify", "not_a_lead"])
    for n in fan:
        g.add_edge("identify", n)
    g.add_edge(fan, "evidence")
    g.add_edge("evidence", "brief")
    g.add_edge("brief", "check")
    g.add_conditional_edges("check", lambda s: "held" if s["problems"] else "request_approval", ["held", "request_approval"])
    g.add_conditional_edges("request_approval", lambda s: "wait_for_sales" if s["outcome"].get("draft_id") else END,
                            ["wait_for_sales", END])
    g.add_edge("wait_for_sales", "finish")
    for n in ("blocked", "not_a_lead", "held", "finish"):
        g.add_edge(n, END)
    return g.compile(checkpointer=checkpointer or InMemorySaver())

Build your own: the AI-era argument

The field changes every quarter. Owning the engine means bending it to the goal the same week. Building this demo found four gaps in OperonX, and all four were fixed, tested and released as 1.12.0 before the talk:

an agent inside a graph lost its questiona real engine bug: a nested graph's merged cell dropped its input and doubled its writes, fixed at the root, with tests
agent["final"]the agent is one node; the next step reads its answer
webhook(...), schedule(...)runs started by an email or by 8 am
MCPClient.call_valuean MCP tool's value, not its text
The honest cost

We maintain it, and it serves our team. It's not a product for everyone. Build only what you'd otherwise fight.

The whole system, live

  1. Pick an email above and press Send as customer. It goes over SMTP to the inbox.
  2. The inbox's webhook starts the OperonX graph: Studio lights it up. Screen, triage, identify, then CRM, calendar and memory beside three research agents, then the brief, the check, and the approval request.
  3. “[Approve?] Brief: …” lands in the inbox. Click Approve: the brief goes to sales and into memory.
  4. Now send an attack. It's held at the gate in milliseconds, and nothing is sent.

The Act 1 agent is one node in this graph. The golden emails gate every deploy (operonx-run golden), and every run is a trace in Studio.
